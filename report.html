Jev is fast. Luna finishes more.

Bottom line: yes, within a clear range. On 42 scripted browser tasks with an exact pass/fail check, Jev's two fast browser variants each land 18 of 42 (42.9%) while Luna and the Jev-then-Luna Hybrid both land 42 of 42, so Jev is dramatically faster and cheaper only on tasks its structured control view can already see cleanly. On the harder real-world browser set, Jev Browser passes 0 of 10 and Jev Ultrafast 1 of 9 on a separate public lane, against 7 of 10 for both Luna and Hybrid; on five native macOS desktop tasks Jev passes 1 of 5 against 5 of 5 for Luna and Hybrid. In short: Jev is genuinely good at short, well-exposed browser controls at a fraction of the cost and latency, and it falls off a cliff on multi-step forms, rich editors, uploads, and native apps - where Luna's slower visual approach, and the Hybrid combination that calls Luna only after a verified Jev miss, reliably finishes the job instead.
What the tests were:
  • Simple tests - 42 scripted browser fixtures (downloads, filters, tables, selects, search); each task has an exact end-state check, scored pass or fail.
  • Real-world browser - 10 longer workflows on live sites (flights, dining, authenticated docs and mail) that need multi-step navigation or sign-in; scored by reaching the named stop point, not just loading a page.
  • Computer use - 5 tasks in native macOS apps (TextEdit, Pages, Keynote, Numbers, Spotify); scored by verifying the requested content is actually on screen at the end.
  • Agent-native apps - a separate authenticated lane (Mail, Calendar, Design, Slides, Content) with its own task count per approach (Jev 8, Luna 5); scored by reaching a safe checkpoint short of sending, saving, or publishing, and not pooled into the Overall leaderboard.

Real-world browser details

These are deliberately harder than the fixture battery: booking stop points, authenticated apps, rich editing, and multi-step navigation. A pass requires the meaningful safe stop point, not a search page. We did not submit purchases, reservations, sends, shares, or payments.

Why Jev Browser is 0 / 10: This is not “zero clicks.” Jev reached partial pages and controls, but none of the ten runs reached its exact verified postcondition. The retained evidence clusters the misses around transport/auth gates, multi-step forms and rich state, and false or incomplete end-state verification. The score therefore measures dependable completion, not whether the browser moved.

How the approaches work

  • Browser path: the wrapper exposes structured page controls and text to the Jev decision model. Some implementations can add DOM/HTML extraction, accessibility, or OCR; “Jev computer use” is not one universal perception contract.
  • Native path used here: Jev's desktop adapter collects macOS Accessibility elements plus Vision OCR candidates. Jev selects a typed action such as click, set value, or type text from that structured snapshot. It is not receiving a raw HTML document from TextEdit or Pages.
  • OCR: Optical Character Recognition turns pixels in a screenshot into guessed words and bounding boxes. It can suggest where “Save” or “Karma Police” appears, but it does not prove that the target is editable, clickable, focused, or successfully changed.
  • Why native is harder: browser controls usually expose stable semantic roles, labels, values, and DOM state. Native apps vary: TextEdit exposed a clean AXTextArea, while rich editors, spreadsheets, canvases, and some media apps can expose sparse or stale semantics. The driver then leans more on OCR, coordinates, keyboard focus, and independent verification.
  • Luna path: Luna operated the visible desktop/browser surface and was required to verify the end state from the UI.
  • Text: Jev can emit literal text when the target and focus are clean. The failure mode is target/focus/semantic editing and verification. Pages is the clearest example: Jev emitted two type actions, reported completion, and still left the Body empty. TextEdit passed because the native text area was a clean target.

Separate driver control: TryCua Cua Driver independently set the same kind of multi-line TextEdit value through a fresh Accessibility snapshot and read it back twice. That control passed, with no model and no leaderboard score: recording · verified screenshot. It proves the native driver can act when the app exposes a clean target; it does not prove that Jev can choose the target or plan the workflow.

Text note: the basic fixtures used a scripted text helper, so those rows measure browser decisions rather than prose generation. The Ultrafast wrapper used a small text model to supply the literal string after Jev selected the target and operation. That helper does not solve focus, caret movement, rich-text editing, keyboard submission, or verification. Luna generated and entered text through its own visual loop. In the native Jev run, the task supplied literal strings to a typed action policy; there was no general-purpose writing model hidden behind the Jev score.

Related implementations and claims: Third Hand, TipTour macOS, and Cua. The benchmark treats a demo's driver, OCR, DOM extraction, keyboard helper, and Jev model as separate components rather than attributing every capability to Jev alone.

Where Jev fails and why

  • Google Flights (real-world browser): typed a natural-language destination string into the field instead of a matched airport, the site returned "No matching locations found," and Jev stopped there.
  • Spotify (real-world browser): reached the public account sign-up wall and stopped; the browser lane has no logged-in session to get past it.
  • OpenTable (real-world browser): blocked by the site's EdgeSuite CDN before the app UI ever loaded.
  • Notion (real-world browser): no verified edit - the run did not produce a confirmable change on the page.
  • File uploads (simple tests): stops at the file-input step every time; the native macOS chooser sits outside Jev's structured control view, and only Hybrid's hand-off to Luna gets past it.
  • Pages (computer use): reported SUBTASK_COMPLETE while the document body stayed empty - a false completion, not a crash.
  • Keynote and Numbers (computer use): ended with blank slide placeholders and an empty spreadsheet table - the file was created but the requested content was never entered or verified.
  • Spotify (computer use): played the wrong Radiohead track.
  • TextEdit (computer use) is the exception that proves the pattern: it passed because the native text area is a clean accessibility target Jev can act on directly, unlike the richer editors above.

Where Luna fails and why

  • Google Drive (real-world browser): search returned the wrong file and the run hung past 20 minutes without finding the private target - the slowest, costliest miss in the set.
  • Figma (real-world browser): stopped at Google's device-passkey confirmation screen, an auth wall it cannot click through.
  • OpenTable (real-world browser, 10-task lane): reached the results page but not the named reservation-details stop point, so it is scored a miss despite getting close.
  • Why Hybrid's cost moves in opposite directions by lane: Hybrid tries Jev before calling in Luna to recover a verified miss, so it lands cheaper than Luna on Simple tests ($0.0069 vs $0.0107 per success) where Jev often succeeds outright - but more expensive than Luna on Computer use ($0.0126 vs $0.0091 per success), because the failed attempt is paid for and then added on top of Luna's own cost.

Takeaways

  • Use Jev for short, exposed controls, navigation, search-and-type, simple selects, and high-volume low-risk decisions.
  • Expect the cliff around drag/drop, uploads, multi-field forms, rich text, spreadsheets, iframes/shadow DOM, and native rich editors where an action can look successful without changing the real content.
  • Use Luna when visual context, recovery, text editing, or long-horizon state matters more than raw latency.
  • Use the hybrid with an explicit postcondition verifier. It is not magic: on native tasks where Jev fails, trying Jev first adds time and cost before Luna recovers. Its benefit is cheap wins plus recovery, not “free” parity.

Limitations

  • Cost estimates, not invoices: every dollar figure is a token-priced estimate translated into a comparison number - several rows are explicitly marked "estimate" in the tables above, not a metered subscription bill.
  • Small sample sizes: 42 simple tasks, 10 real-world browser tasks, 5 computer-use tasks, and 5-8 agent-native-app tasks depending on approach. A handful of flipped outcomes would move the percentages noticeably.
  • Replay, not one live run: Hybrid's real-world-browser score pairs Jev's retained 0/10 attempt with a separately recorded Luna recovery run - staged evidence, not one interleaved live turn handing off task by task.
  • Jev Ultrafast's denominator is 51, not 57: it was never run on the computer-use lane, so its Overall rate (marked with an asterisk) is not directly comparable task-for-task with Luna and Hybrid's 57.
  • Curated task sets: the 10-task real-world set and the 5-task desktop set were chosen to cover known failure modes, not sampled at random from a larger pool - read them as illustrative, not statistically representative.
  • One machine, one operator, one day: there is no repeat-run variance data, and results can shift with a different environment or a site's own changes.
  • Harness scope: Luna and Hybrid drive the ChatGPT desktop app's connected-Chrome bridge, which does not execute page JavaScript. A few Jev-side JS probes are reported separately as deterministic upper bounds and are not part of the four-system scores.
