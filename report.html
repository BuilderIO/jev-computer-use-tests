Browser tools check

For a general browser-agent comparison, page inspection, accessibility data, and JS execution are fair browser tools and should be available by default. This check is separate only because its 14/14 and 42/42 results were deterministic scripts, not Luna choosing and verifying tools. The next matched run should give Luna and Hybrid the same browser-tools interface and report them as separate “+ browser tools” rows.

Jev + JS fallback replay42 / 42100%1.81 s$0.00542$0.00012918 retained Jev wins plus 24 deterministic JS replays of Jev failures; an upper-bound replay, not a planner run
Why it is not in the headline score: Folding a deterministic script into Luna would overstate what Luna itself did. That is a measurement limitation, not a claim that JS access is unfair or out of bounds. The current results show the browser-tools ceiling; a model-controlled rerun is needed to measure agent performance with that ceiling available.

What Luna actually missed: In the repeated 42-task browser run, Luna passed 39/42; the three misses were the file-upload fixture, once in each pass. These browser runs used Codex’s visible in-app browser through CUA, not Playwright/CDP or a Chrome remote-debugging adapter. That CUA surface exposed screenshots, clicks, and typing, but no file-picker/upload primitive, so Luna could not attach the fixture. This is a limitation of that harness configuration, not evidence that Luna or Codex can never upload files. A browser adapter with a native file chooser or file-input binding could support uploads. In the separate ten-task real-world browser run, the non-passes were OpenTable (results page, not the named reservation-details boundary), private Drive (wrong search result and a hang beyond 20 minutes), and Figma (Google device-passkey boundary). Neither headline Luna result had model-controlled JS evaluation enabled. The 14/14 JS probe and 42/42 Jev-plus-JS replay are deterministic upper bounds, not Luna runs.

Would JS have raised Luna’s score? We cannot honestly add points from the existing data. JS would likely help inspect or query difficult DOM state, but it would not solve the missing file-picker primitive, a passkey challenge, or an authorization problem. The only defensible estimate today is “unknown”; a matched Luna-plus-JS rerun is required.

Real-world browser details

These are deliberately harder than the fixture battery: booking boundaries, authenticated apps, rich editing, and multi-step navigation. A pass requires the meaningful safe boundary, not a search page. We did not submit purchases, reservations, sends, shares, or payments.

Why Jev Browser is 0 / 10: This is not “zero clicks.” Jev reached partial pages and controls, but none of the ten runs reached its exact verified postcondition. The retained evidence clusters the misses around transport/auth gates, multi-step forms and rich state, and false or incomplete end-state verification. The strict score therefore measures dependable completion, not whether the browser moved.

How the approaches work

  • Browser path: the wrapper exposes structured page controls and text to the Jev decision model. Some implementations can add DOM/HTML extraction, accessibility, or OCR; “Jev computer use” is not one universal perception contract.
  • Native path used here: Jev's desktop adapter collects macOS Accessibility elements plus Vision OCR candidates. Jev selects a typed action such as click, set value, or type text from that structured snapshot. It is not receiving a raw HTML document from TextEdit or Pages.
  • Luna path: Luna operated the visible desktop/browser surface and was required to verify the end state from the UI.
  • Text: Jev can emit literal text when the target and focus are clean. The failure mode is target/focus/semantic editing and verification. Pages is the clearest example: Jev emitted two type actions, reported completion, and still left the Body empty. TextEdit passed because the native text area was a clean target.

Text note: the controlled fixtures used a scripted text helper, so those rows measure browser decisions rather than prose generation. The Ultrafast wrapper used a small text model to supply the literal string after Jev selected the target and operation. That helper does not solve focus, caret movement, rich-text editing, keyboard submission, or verification. Luna generated and entered text through its own visual loop. In the native Jev run, the task supplied literal strings to a typed action policy; there was no general-purpose writing model hidden behind the Jev score.

Related implementations and claims: Third Hand, TipTour macOS, and Cua. The benchmark treats a demo's driver, OCR, DOM extraction, keyboard helper, and Jev model as separate components rather than attributing every capability to Jev alone.

Takeaways

  • Use Jev for short, exposed controls, navigation, search-and-type, simple selects, and high-volume low-risk decisions.
  • Expect the cliff around drag/drop, uploads, multi-field forms, rich text, spreadsheets, iframes/shadow DOM, and native rich editors where an action can look successful without changing the real content.
  • Use Luna when visual context, recovery, text editing, or long-horizon state matters more than raw latency.
  • Use the hybrid with an explicit postcondition verifier. It is not magic: on native tasks where Jev fails, trying Jev first adds time and cost before Luna recovers. Its benefit is cheap wins plus recovery, not “free” parity.
